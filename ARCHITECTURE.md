# Architecture

How the code is put together, where things belong, and the rules that keep it
working. The README covers what the product does and how to deploy it; this file
is for whoever changes the code next (a person or an AI agent).

## What it is

A script-production workspace for one team: clients → shoots → script batches →
scripts, with writers, reviews, deadlines, reminders and delivery records.
Roles are **Admin** (`owner` in code), **Manager**, **Writer** and **Editor** (read-only, never given scripts). An Editor has one kind (`users.editor_kind`): a **video editor** (`short_form`, or no kind, as every editor was before kinds) or a **thumbnail designer** (`thumbnail`), who makes the videos' thumbnails in their Studio.

- **Server:** Fastify 5 on Node 22 in `server/`. It serves the JSON API under `/api/` and, in production, the built client.
- **Database:** PostgreSQL via `pg` in production. Locally, in the demo and in tests it uses PGlite, an embedded Postgres. Both engines run the same SQL and the same migrations.
- **Client:** React 19, react-query 5 and react-router 7, built with Vite, in `client/`.
- **Shared:** domain rules used by both sides live in `shared/`. That folder imports nothing from `server/` or `client/`.

### Where to add things

- **A new API endpoint.**
  1. Put it in the module that owns the resource, or in a new `register…Routes(app, ctx)` registered in `buildApp`.
  2. Begin the handler with a guard (see Access below).
  3. Validate input with `parse(schema, req.body)` and reuse the `zs` fields.
  4. Add the route to the `ACCESS` table in `test/access.test.ts`. The test fails until you do.
- **A new rule both sides need** (a status, a deadline, a permission): add it to `shared/`. Never copy it into a page or a route.
- **A schema change:** append a migration to `MIGRATIONS`. Prefer additive changes, and do backfills as function migrations.
- **A new environment variable:** add it to `Config` in `server/config.ts`, with its default and range, and to `.env.example`. Server code never reads `process.env` directly; the entry points hand it to `loadConfig`.
- **A new page:** add a route in `client/src/main.tsx` and a nav item in `Shell.tsx`. Build it from `ui.tsx` primitives and `tokens.css`.
- **A job that must never run twice at once:** add an id to `LOCKS` in `server/db.ts` and take it with `pg_advisory_xact_lock` inside a transaction.

## A request, start to finish

1. **CSRF** (`app.ts`): any `/api/` request other than GET or HEAD needs the header `x-scale-media: 1` (`CSRF_HEADER`). If an `Origin` header is present, its host must match. The server never grants CORS.
2. **Who is asking** (`recording.ts`):
   - The `sm_session` cookie is resolved against the **real** database. Only the token's SHA-256 is stored; a session lasts 30 days and is not extended by use.
   - This sets `req.realUser` (who signed in) and `req.user` (who the request acts as). They differ only during View as.
   - **View as** is read-only on the real workspace. Writes are refused, except a few background writes that quietly do nothing.
   - **Recording mode** sends the session's requests to a cloned `rec_<12 hex>` schema through `AsyncLocalStorage`, so `ctx.db` is the practice copy and route code doesn't need to know.
   - It **fails closed**: a write whose `x-scale-recording` header names a practice copy that no longer exists gets 409 `recording_ended`. It never falls through to the real data. The same applies once an admin is demoted. Sign-in and `/api/admin/*` calls are exempt, because they only change the real sign-in.
   - `/api/auth/*` and `/api/admin/*` always use the real database.
3. **Handler:** guard → `parse` → work. A change to a batch or its scripts runs in `db.tx` and locks rows first: the batch row (`for no key update`) for batch-wide changes, then the script rows (`for update`) it touches. Other transactional changes lock their own row (a client, a shoot). Simple single-record edits (a team member, client, shoot or editor) write the row and its history line without a transaction.
4. **Errors** (`app.ts`):
   - An `HttpError` becomes `{ error: { message, fields?, code? } }` with its status code.
   - A unique violation that slipped past the explicit checks becomes 409 `duplicate`.
   - Anything else is logged and becomes a 500 that says nothing was saved.
   - The client's `api()` turns all of these into an `ApiError`, which forms show beside the field it names.
5. **Audit** (`audit.ts`, `onResponse`): page views and refused attempts go to `audit_log`, but not in Recording mode. During View as they are attributed to the admin.

## Access

- **Guards** (`server/auth.ts`):

  | Guard | Who passes |
  |---|---|
  | `requireUser` | anyone signed in |
  | `requireManager` | Admin or Manager |
  | `requireAdmin` | Admin only |

  Role checks use `isManager`, `isAdmin`, `isEditor` and `canWrite` from `shared/workflow.ts`. Never compare role strings in routes.
- **Editors** get only the routes listed in `server/editor-access.ts` for their kind (`editorRoutesFor`: `BASE` for every editor, plus `BY_KIND`; during View as it's the viewed person's kind); every other route is refused before it runs with a 403 worded for their kind (`EDITOR_REFUSAL`, code `editor`), so a new route is closed to editors until it's added there on purpose. Their reads are also scoped to finished (approved or delivered) work. Thumbnail designers add only their Studio's eleven routes (below): its seven (their portfolio among them), and the four of their reference boards. Of the Editors routes, video editors get only `GET /api/editing/me`, `POST /api/editing/focus` and `GET /api/editing/script-pdf/:batchId`, all for the session user's own videos (matched by email; a video is theirs only when it's assigned to them in Timeliner: `OWNER_IDS` in `server/editing.ts`): focus refuses a video that isn't theirs, and the scripts PDF a batch they have no video from (403; opened in a browser tab, it answers with a short page saying why rather than JSON). The managers' match notes are never in what editors get, nor what the read found across the workspace (`sync.counts`). `GET /api/editing`, `POST /api/editing/sync` and the pins (`POST` and `DELETE /api/editing/videos/:id/pin`) are `requireManager`.
- **Stored files** (`GET /api/files/:id`) have one rule per person, chosen in `server/routes/clients.ts` with the SQL in `server/files.ts`:

  | Who | May open |
  |---|---|
  | Writers | any file something live refers to: a resource, a document sent, a review, a past script |
  | Video editors | `EDITOR_FILES`: resource files, past scripts, approved reviews, and documents whose scripts are all finished |
  | Thumbnail designers | `EDITOR_FILES`, or `DESIGNER_FILES` bound to their own id (`$2`): the tray of a brief that's theirs now, options in rounds they sent, the current winner of every brief not cancelled for a client they have or had a brief for, and the images they uploaded to their own reference boards while the ref is on a board. Never another designer's unpicked options, not even rounds sent on a brief before it was given to them |
  | Managers | the writers' rule, or `SENT_OPTION_FILES`: options in sent rounds, never a designer's tray |

  Thumbnail options are never in the writers' rule or `EDITOR_FILES`, so writers and video editors can't open them. No rule but `DESIGNER_FILES` names `thumbnail_refs`, and it only with the caller's own id, so a ref's upload opens for nobody else: not a manager, another designer, a writer or a video editor.

  Once a rule lets a file through, a thumbnail picture (`THUMB_PICTURE`: an option's image or a reference board's upload, whose id names that upload for good) is sent with `Cache-Control: private, max-age=86400, immutable` (`THUMB_FILE_CACHE`), so a wall of them loads once a day; every other file keeps `private, max-age=300` (`FILE_CACHE`). The header never decides who may open a file. Signing out (`POST /api/auth/logout`) answers with `Clear-Site-Data: "cache"`, so a shared browser forgets what it kept before the next person signs in.
- **Thumbnail Studio** (`server/thumbnails.ts`): `GET /api/studio` and `GET /api/thumbnails/:id` are `requireUser`, then refused (403) before anything is parsed unless the caller is a thumbnail designer or a manager. Adding an option, taking one out and sending a round are for thumbnail designers only, and only on a brief that's theirs now (404 otherwise, so another designer's brief doesn't leak). The board, New thumbnail, Edit (`PATCH`) and decisions are `requireManager`. A designer always gets their own Studio, from the session; a manager names one with `?userId=` (an active thumbnail designer, else 404) and gets it read-only. Only a brief's current designer gets its unsent tray; managers get how many options are in it, never the images. Who sees what is `present()`'s `View`: a brief's current designer sees rounds someone else sent on it with their notes and decisions but without their options (the winner aside), and a designer the brief was taken from reads only the rounds they sent (`viewer: 'past_designer'`), with nothing of the brief since: no later decision, tray count or state (once someone else has sent a newer round, it's just still open, `to_design`). Pins are on a round's options, so `present()` gives a designer a decision's pins only on rounds they sent (none on someone else's, nor on `brief.decision` when the newest round isn't theirs); managers get every decision's. Beside a brief, `recentWinners` are the client's winners by anyone, but a designer sees `standout` only on their own (how a manager rated another designer's pick is that designer's).
- **Went live and the portfolio** (`server/thumbnails.ts`): `POST /api/thumbnails/:id/published` and `GET /api/thumbnails/timeliner-videos` are `requireManager` and on no editor's list. A brief's `timelinerTaskId` and `video` (the Timeliner video it's for) are only in a manager's view: `present()` leaves the keys out for designers. Its `live` mark is shown to whoever sees the pick (null for a designer the brief was taken from whose round isn't the newest), but the Test & Compare winner's picture (`testWinner.url`) only to managers, and to a designer when it's their own option or the pick: another designer's unpicked option stays a letter. `GET /api/studio/portfolio` is `requireUser`, then refused (403) before anything is parsed unless the caller is a thumbnail designer or a manager, as `GET /api/studio` is: a designer always gets their own, from the session (`?userId=` is ignored); a manager names an active thumbnail designer with `?userId=` (404 otherwise) and gets it read-only. `?clientId=` and `?month=` (YYYY-MM, `isYearMonth`) are checked with zod (400 `fields`). Nothing in it compares one designer with another.
- **Second look** (`server/second-look.ts`): `POST /api/thumbnail-options/:id/second-look` is `requireUser`, then refused (403) unless the caller is a thumbnail designer, and 404 unless the option is live and theirs: uploaded by them, in the tray of a brief that's theirs now or in a round they sent. It's private to its maker: `present()` puts it on that option (`secondLook`, null until they ask) only when the viewer is the designer who uploaded it, and leaves the key out for managers and everyone else, an Admin viewing as the maker included (`View.viewingAs`, from `req.viewingAs`). While an Admin views as a designer the route is 403 `viewing_as`, even in Recording mode, so practice never makes a billed read against the designer's limits, and `Bootstrap.secondLook` is false, so the button doesn't show.
- **Content roadmaps** (`server/roadmaps.ts`): `GET /api/roadmaps`, `GET /api/roadmaps/:id` and `POST /api/roadmap-tasks/:id/done` are `requireUser` and on the editors' `BASE` list (everyone reads roadmaps); ticking is refused (403) unless the caller is a manager or the person on the deliverable's role. `POST /api/roadmaps/import`, `PATCH /api/roadmaps/:id/roles/:key` and `DELETE /api/roadmaps/:id` are `requireManager`; the import is 403 `viewing_as` while an Admin views as someone (even in Recording mode), 503 `not_configured` without `ctx.roadmapReader`, and 400 `fields.file` for anything that doesn't start `%PDF-`.
- **Brand kit** (`server/routes/clients.ts`): `GET /api/clients/:id` (on the editors' `BASE` list) carries the kit (`brand`, null when there's none) to everyone who may see the client, editors included. Its `recentWinners` (at most `RECENT_WINNERS`) are every winner for managers; for a thumbnail designer only those `DESIGNER_FILES` lets them open (so none until they have or had a brief for the client), with `standout` only on their own; the key is left out for writers and video editors. `PATCH /api/clients/:id/brand` is `requireManager` and on no editor's list: 404 for an unknown client, 409 `archived` for an archived one.
- **Reference boards** (`server/refs.ts`): every `/api/thumbnail-refs` route is `requireUser`, then refused (403) unless the caller is a thumbnail designer (managers included: nobody else has boards), and acts only on the session designer's own refs (another's is 404). A ref added as JSON is exactly one of a current winner they may open (`DESIGNER_FILES`, else 404) or a live resource whose file is a picture (400 `fields.resourceId` otherwise); an upload is sniffed and stored like an option (`uploadedImageInfo`, `asImageUpload`; anything but PNG, JPEG or WebP is 400 `fields.file`). The list shows only refs whose picture they can still open (a winner no longer picked, or a resource since removed, drops out), and `PATCH` is 404 on those too.
- **AI brief ideas** (`server/brief-ideas.ts`): `POST /api/thumbnails/suggest` is `requireManager`; while an Admin views as someone it's 403 `viewing_as`, even in Recording mode, and `Bootstrap.briefIdeas` is false, so the button doesn't show.
- **Past thumbnails from YouTube** (`server/youtube.ts`): `POST /api/thumbnails/youtube/lookup` and `POST /api/thumbnails/youtube/import` are `requireManager` and on no editor's list; while an Admin views as someone they're refused like every other change, and Recording mode writes the import to its practice copy (`ctx.db`). Without a reader (`ctx.youtube`) both are 503 `not_configured`. The import's designer must be an active thumbnail designer (400 `fields.designerId`, as New thumbnail) and each client one that exists and isn't archived (400 `fields["items.<i>.clientId"]`). An imported brief is an ordinary picked brief from then on, so who sees it and who opens its picture follow the existing rules (its option is uploaded by the designer, and it's a current winner for `DESIGNER_FILES`, recent winners and the brand kit); `brief.imported` and `win.imported` go to everyone who sees the brief or win.
- **Script actions:** every status change goes through `applyScriptAction`. It locks the rows and checks each one with `checkAction` and `ACTION_RULES`. Writers can act only on their own scripts.
- **Ownership checks** live in the route: the assignee on a script edit, `isAssignedTo` for blockers and resources. A personal view (My work, Today, to-dos) always gives a writer their own data, from the session. A manager may name someone with `?userId=`, and may ask for the whole team on Today (no `userId`) and to-dos (`?all=1`). Notifications always use the session user.
- **Admin protection:** only an Admin can grant the Admin role or change anything on an Admin's account. The last Admin can't be removed or demoted. Temporary passwords are shown only to managers, and never an Admin's to a non-admin.
- **Sign-in throttle:** 8 wrong passwords per address and account, and 30 per account from any address, in 15 minutes. The address comes from `X-Forwarded-For`, trusted as far as `TRUST_PROXY` allows.

## Data

- **`Db`** (`server/db.ts`) has `query`, `one`, `tx`, `close` and `withSchema`.
  - Route code always uses `ctx.db`, which follows Recording mode.
  - `ctx.realDb` is only for session and sign-in plumbing (`recording.ts`), for reading file contents that stay on the real workspace (streamed by `/api/files/:id`, and an option's image and its references sent for a second look, read the same way), and for the timed background reads of calendars and Timeliner (`startCalendarSync`, `startTimelinerSync`), which never write to a practice copy.
- **Migrations** run at start-up, in order, one transaction each, under `LOCKS.migrations`.
  - SQL migrations are split into statements on `;` at a line end. Anything that can't be split that way is written as a function migration.
  - Function migrations import `shared/dates.ts`, and migration 43's backfill (`fillYoutubeVideoIds`) reads links with `youtubeVideoId` from `shared/workflow.ts`. Changing those helpers changes what a fresh database's backfill produces.
- **Optimistic concurrency:** scripts carry a `version`, and a stale edit gets 409 `stale` (the script dialog sends all its fields with the version it started from). Edit batch, Edit client and Script titles send only the fields the person changed, compared with a snapshot taken when the dialog opened. Other edit forms (deadline rules in Settings, team members, to-dos) still send the whole form, so a route must compare the input with the stored row before treating a field as changed, as `PATCH /api/users/:id` does.
- **Files** are stored in Postgres, in the `files.data` column (`server/files.ts`). An upload is read in 4 MB pieces into a scratch table and written as one value (linear in the file's size; appending piece by piece would be quadratic), and downloads stream back out in 512 KB pieces. A stored file never changes under its id, which is why a thumbnail picture can be kept by the browser for a day (`THUMB_FILE_CACHE`). A single value can't exceed 1 GB, and `UPLOAD_LIMIT_MB` caps uploads at 100. Names are cleaned up by `storedFileName`, and executables are refused.
- **Timeliner copy** (`server/editing.ts`): `timeliner_tasks`, `timeliner_members`, `timeliner_names` (brands, projects, sub-folders, with when each was made) and `timeliner_brand_members` (who is on each brand, with their brand-level role and whether the access is automatic) are a copy of Timeliner, written only by its reads and webhook. `settings.timeliner_sync_counts` keeps what the last complete read found (videos, people, clients, skipped) for the tab's sync line. Each task row also stores its match (`client_id`, `batch_id`, `script_number`, and `match_how`, `match_note`, `match_check`, `match_kept`), worked out again after every write by `rematch`. The site's own layer is `editor_focus` (one row per person: the video they're on, `on` or `paused`, with time worked), `editing_done` (Done marks, which count until Timeliner moves the video) and `timeliner_video_pins` (a manager's "this video is from that batch", or from none). `timeliner_removed` keeps removed task ids for a day; `timeliner_editor_clips` remembers each editor's raw clips, clip by clip, for 45 days with the batch each was last matched to (so a clip moved to another shoot takes its memory with it), because the clips are trashed soon after the titled videos are made. `has_video` on a task row says it held a video file, so a document uploaded to it later is notes on the video, while one uploaded to a task first read with no file is a scripts PDF. Nothing here writes to Timeliner.
- **Scripts PDFs** (`server/timeliner.ts`): `timeliner_pdfs` links each shoot's scripts PDF (by its task id, or `file:<id>` for a file put straight into a project) to its batch, once, with its version, newest file and step, and `gone_at` when trashed. Only an upload or a manager's pick creates (or moves) a link; reads only keep it current. Editors are offered a batch's PDF only when it delivered scripts still delivered there, or everything there is delivered: one that delivered nothing may hold scripts that aren't approved. Timeliner's download links are never stored: `GET /api/editing/script-pdf/:batchId` fetches one and redirects to it.
- **Thumbnail Studio** (`server/thumbnails.ts`, migrations 39, 40, 42 and 43):
  - `thumbnail_briefs`: a manager's brief (client, optional shoot, the video's title as typed, since scripts have no titles; what it should show, words on the image, options wanted 1–6, due date, designer, `cancelled_at`).
  - `thumbnail_rounds`: numbered per brief. `sent_at` null is the designer's private tray, at most one per brief (`thumbnail_rounds_tray_key`); `created_by` is whoever sent it, which is what a designer the brief moved away from keeps reading.
  - `thumbnail_variants` (options to people): lettered A–F, unique among the live ones in a round. Each is an image in `files` whose `mime`, `width` and `height` come from its own bytes (`server/images.ts`); the browser's type is never stored or served. Taken out with `removed_at`, never deleted.
  - `thumbnail_decisions`: pick an option, or ask for changes (a note is required). The newest on a round counts (`created_at desc, id desc`); earlier ones stay as history. A pick can be `standout`; the database refuses a standout that isn't a pick (`thumbnail_decisions_standout_check`), and the route says so first (400 `fields.standout`).
  - `thumbnail_pins` (migration 40): a decision's numbered notes on spots of the round's options, up to `MAX_PINS`, each on a live option of that round (400 `fields.pins` otherwise). `x` and `y` run 0 to 1 across and down the picture itself (checked by the database), `n` is 1, 2, 3… in the order sent (unique per decision: `thumbnail_pins_number_key`, also the index they're read by), with the note and an optional tag. They're never changed: the pins a round shows are its newest decision's (`currentPins`), and an earlier decision's stay with it as history.
  - `thumbnail_second_looks` (migration 40): one kept second look per option (`variant_id` is the key; `result` is the tidied answer as jsonb), since an option's image never changes. Kept only while the option is live, and tidied again (`tidySecondLook`) whenever it's read.
  - **Where a brief stands is never stored.** `thumbnailState` in `shared/workflow.ts` works it out: cancelled; to design, or drafting once the tray has an option, before anything is sent; in review while the newest sent round has no decision; else changes or picked. SQL agrees through `THUMB_LATEST_SENT` and `THUMB_WINNER` in `server/files.ts`, and every count (the menu badges, the board, the Studio) is counted from these rows.
  - A new round supersedes one still waiting, so a decision on the older one is 409 `stale`; a send that finds nothing unsent after a round went (a double tap, another tab) is 409 `sent`, and taking out an option already sent or removed is 409 too, so the stale page refreshes. Deciding again on the same round takes back the unread notifications about the last decision (`notifications.thumbnail_decision_id`, set through `notify`'s `thumbnailDecisionId`) and its celebration if it hasn't been seen (`moments.thumbnail_decision_id`).
  - A pick is told to whoever sent the round (it goes on their Wall of wins) and, when the brief has moved to someone else since, to its designer too; changes are told to the brief's designer, who makes the next round. Only an open brief can be cancelled (409 `picked` otherwise): a pick is the brief's outcome.
  - A pick is celebrated, in the decision's transaction, for whoever made the option while they're an active thumbnail designer (`recordThumbMoment` in `server/moments.ts`): `thumb_picked`, or `thumb_standout` when it's marked Standout (migration 40 swaps `moments_kind_check` for one with both). Its moment has no batch (`batch_id` null) and names its decision (`thumbnail_decision_id`); the key (`thumbMomentKey`: kind, person and decision, since `moments.dedupe_key` is unique across the whole table) records it once. The payload carries the picked option for the dialog's frame, and whether it came from the brief's first round sent (the bigger celebration: `pickCelebration`). Asking for changes is never celebrated. `GET /api/moments` leaves a pick's moments out for anyone who isn't a thumbnail designer now (its picture and brief wouldn't open for them); they stay unseen.
  - Reassigning a brief takes the old designer's tray options away; the unsent round stays, and the next designer takes it over with their first upload. An old designer who sent nothing on it loses their unread notifications about it, since it would open "not found" for them. An upload is one image per request: the file is stored first in the `db.tx`, then the brief row is locked, then the round.
  - **Went live** (migration 42): a picked brief's mark is kept on its row: `published_url` (https, at most `LIVE_LIMITS.url`), `published_on` (the day), `published_by` and `published_at` (who marked it last, and when), `test_winner_variant_id` (YouTube Test & Compare's winner, a live option of one of the brief's sent rounds, never a tray's: 400 `fields.testWinnerOptionId` otherwise) and `test_note` (at most `LIVE_LIMITS.note`). Anything marked needs the day: the database refuses a link, test winner or note without `published_on` (`thumbnail_briefs_published_check`), and the route says so first through `liveProblems` (400 `fields.publishedOn`), so taking the mark back sets every column to null. `POST /api/thumbnails/:id/published` locks the brief row first (`for update`), is 409 `not_picked` unless it's picked now, lays the keys it was sent over the kept mark (`mergeLive`: a key left out keeps its value, so the dialog sends only what the manager changed, `liveChanges`, and two managers changing different fields never undo each other), checks the result (`liveProblems`; a test winner only when it's a new one), takes the mark back when the result is empty (every key sent as null does it), and writes and logs (`thumbnail.live`, `thumbnail.unlive`) only when something changed. Marking it tells the picked option's maker once per pick, while they're an active thumbnail designer (`thumbnail_live`, keyed `thumbLiveKey(briefId, optionId)`, linking to their card with `portfolioPath`, `thumbnail_decision_id` the pick's); taking it back deletes that message while it's unread, and a read one stays in their history without keeping a later pick of another option from being told. The mark is the pick's: a decision (in its own transaction, with the brief row already locked) that changes the pick, to another option or to changes asked, takes the mark back the same way; picking the same option again keeps it and moves its message's `thumbnail_decision_id` to the new decision, so the usual take-back of the old decision's unread messages leaves it. `live` is presented only while the brief is picked and marked.
  - **The Timeliner video a brief is for** (migration 42): `thumbnail_briefs.timeliner_task_id`, a task id from the site's copy of Timeliner with no foreign key (the copy loses rows), indexed (`thumbnail_briefs_timeliner_idx`) to find the brief of a video. New thumbnail and Edit check it is a task matched to the brief's client (`timeliner_tasks.client_id`) and not a scripts PDF (400 `fields.timelinerTaskId`); `PATCH` checks only a change, so a link kept from before stays after the copy loses that video, and null unlinks it. The picker (`GET /api/thumbnails/timeliner-videos`) lists the client's videos that `offersTimelinerVideo` takes (titled, never a raw clip; open, or Posted in the last `TIMELINER_VIDEO_DAYS`), newest made first, with the brief already naming each and `settings.timeliner_synced_at`. A brief reads its video through a left join of `timeliner_tasks` (its title, step, as `step_label` or `TIMELINER_STEP_LABEL`, and whether it's Posted), all null once the copy has lost it. The board's "Posted in Timeliner — mark it live?" (`toMarkLive`: picked, not marked, the video Posted, by `asksToMarkLive`) is worked out on every load; nothing is stored. Nothing here writes to Timeliner, and video editors' screens and the matching never read it.
  - **A designer's portfolio** (`GET /api/studio/portfolio`) is every current winner they made (`loadWins`), each with its round story (`roundStory`) and its mark, and their growth (`portfolioGrowth`), all worked out from the rows on every load. Both read every brief they sent a round on or made an option for, cancelled ones included, through `loadBriefs`' rounds as stored, never one viewer's share of them (`present()`). Months are the workspace's time zone (`monthOf`); the filters narrow only the cards, never the client and month lists, the total or the growth. Growth covers the last `GROWTH_MONTHS` months: picks are current winners they made, by when the pick was made (deciding again, or a cancel, takes one away); the first-round pick rate is `pct` of those picked from the brief's first round sent; standouts are those marked Standout; note themes count the tags on the pins of the decision that counts on each round they sent, decided in those months. A cancelled brief counts for nothing.
  - **Past thumbnails from YouTube** (migration 43, `server/youtube.ts`): `thumbnail_briefs.imported_from` (null, or `youtube`: `thumbnail_briefs_imported_from_check`), `imported_at`, `imported_by`, and the video's `youtube_video_id`, `youtube_channel` and `youtube_channel_url` (only ever `https://www.youtube.com/…`, through `youtubeChannelUrl`). A video is on at most one brief that isn't cancelled: the unique partial index `thumbnail_briefs_youtube_key` (`where cancelled_at is null`). Migration 43 is one function, so its steps run in order in its transaction: the columns and check, then `fillYoutubeVideoIds` (a brief already marked live with a YouTube link takes its video's id; of two live briefs on one video the one made first keeps it and the later is logged and left null; cancelled briefs keep theirs), then the index. The server never fetches a pasted link: `youtubeVideoId` reads the id, and the reader builds its own addresses. An import reads YouTube again for each video (never a picture from the browser), at most 4 at a time, then adds them one by one in the order sent, each in a `db.tx` of its own (`addPastThumbnail`): the picture stored first (`bufferFile`, `asImageUpload`, `storeFile`, `uploaded_by` the designer), the client checked again, then the brief (title, client and designer as chosen, `created_by` and `published_by` the manager, `published_url` `youtubeWatchUrl(id)`, `published_on` the day it went live, options wanted 1), round 1 created and sent by the designer, option A uploaded by them, and the manager's `pick` (standout false, no pins), all three at `importedRoundAt` (noon on that day in the workspace's time zone, so it's a pick of that day and month), then the activity line `thumbnail.imported`. A video already on a live brief is skipped and named before YouTube is asked, and a 23505 on `thumbnail_briefs_youtube_key` (`isYoutubeKeyClash`: two imports racing) is the same skip with nothing of it kept; one item never fails the others. An import records no celebration and no went-live message: the designer is told once (`tellImported`: `THUMBNAIL_IMPORTED_NOTIFICATION`, a pick's type, keyed `thumbImportKey`, linking to `portfolioPath()`, naming no decision), only when something was added. Its round story is only where it came from (`roundStory` on `StoryBrief.importedFrom`, which `storyOf` passes), and growth counts it in its month's picks (`importedPicks`) but leaves it out of the first-round rate (`roundPicks`). The board's `since` also takes briefs imported since then (`imported_at`), since their picks are backdated, and the Studio's just-picked card ignores imports. The went-live route keeps `youtube_video_id` in step with the link on briefs that weren't imported: a new link sets it to `youtubeVideoId(url)` (null for any other link), checked first against other live briefs (409 `youtube_taken`, `fields.url`, naming that brief; the index decides a race the same way); taking the mark back (`takeBackLive`, also when a decision changes the pick) clears it. An imported brief always keeps the video it came from, whatever its link says. A cancelled brief keeps its video too, so reopening it while that video is on another brief that isn't cancelled is 409 `youtube_taken`, naming that brief (the index decides a race the same way).
- **Content roadmaps** (migration 44): `roadmaps` (title, month as YYYY-MM, brand, summary, the IANA zone its times are in, `default_time`, the playbook as jsonb `extras`, the PDF's file name, `removed_at`), `roadmap_roles` (one row per kind of job, keyed `(roadmap_id, key)`, with the person on it, `user_id`), `roadmap_videos` and `roadmap_tasks` (each deliverable's step, day, optional time, role, and `done_at`/`done_by`). A deliverable's owner is its role's person, never stored on the task, so moving a role moves its work. Progress, overdue and the counts are worked out from the task rows on every load, in the roadmap's own zone (`taskState`). The PDF isn't stored.
- **Brand kits, reference boards and Settings → Editors kinds** (migration 41):
  - `client_brand`: one row per client (`client_id` is the key), made on a manager's first change. `colours` is a jsonb list of `{ name, hex }` (at most 12: `client_brand_colours_check`), `fonts` a list of `{ name, url, resourceId }` (at most 6: `client_brand_fonts_check`; both checks refuse a value that isn't a list rather than erroring), with `dos`, `donts`, `updated_by` and `updated_at`. Hex is kept in capitals (`normalizeHex`), and the lists are written as `JSON.stringify(…)` with `$n::jsonb`. `PATCH /api/clients/:id/brand` locks the client row (`for update`) first, compares the input with the kept kit through `brandChanges` (the same comparison the form makes), writes and logs (`client.brand`, naming the fields) only when something changed. A new font `resourceId` must be a live resource of this client with a stored file (400 `fields.fonts`); one the kit already names may stay after that resource is removed, and then reads with `file: null` (`loadClientBrand`). Colour problems are 400 `fields.colours`, font problems `fields.fonts`.
  - Resources can now be a `logo`, `reference` or `font` (`resources_category_check` swapped the way migrations 6 and 21 swap theirs). The Brand kit shows logos and references (as pictures when `isPictureMime`) and font files; font files are ordinary resource uploads, served as downloads.
  - `thumbnail_refs`: a designer's (`user_id`) ref on a client's board or the general one (`client_id` null), with a caption, taken off with `removed_at`, never deleted. Exactly one of `file_id` (an upload of theirs), `variant_id` (a winner) and `resource_id` (a client's picture) is set (`thumbnail_refs_source_check`: `num_nonnulls(…) = 1`). `thumbnail_refs_user_idx` serves a designer's boards, `thumbnail_refs_file_idx` the `DESIGNER_FILES` lookup. At most `MAX_REFS` refs per designer that they can still open (409 `full`; a winner un-picked or a resource removed leaves their boards and stops counting, since they couldn't take it off): checked before an upload is read, then again after the designer's `users` row is locked (`for no key update`), which every add takes after storing the file, as option uploads do. An add from a winner or a resource checks, inside that transaction, that the new ref still opens, or adds nothing. The same winner or resource twice on one board is 409 `duplicate`. A `PATCH` locks the designer's `users` row first, as an add does, then the ref row, and writes only what changed.
  - `editors.editor_kind` (null, `short_form` or `thumbnail`; only the value is checked, `editors_editor_kind_check`, since that table has no role). The form sends every field, so `PATCH /api/editors/:id` compares the kind with the stored row, and keeps it when it's left out. The Editors tab (`loadEditing`'s `offSite`) takes only entries where `isVideoEditorKind(editor_kind)`.
- **Retention:** the reminders run deletes expired sessions. It also deletes `audit_log` page views, and anonymous sign-in records, after 400 days. Activity and everything else is kept.
- **Single instance:** some state lives in the server's memory: the sign-in throttle, View-as and Recording-mode state, the Paste-notes, second-look and brief-ideas rate limits, the de-duplication of page views, and Timeliner's download links for scripts PDFs (until 10 minutes before they expire). A restart clears it, and it isn't shared between instances, so run one web instance. The reminders and migrations are safe with several, because they use advisory locks.

## Background work and outside services

- **Reminders** (`server/reminders.ts`):
  - They run every `REMINDER_INTERVAL_MINUTES` inside the server (`REMINDERS=off` turns them off), or from `npm run reminders` on a cron, which needs `DATABASE_URL`.
  - Each run takes `LOCKS.reminders`, and notifications are de-duplicated by key, so overlapping runs are harmless.
- **Calendar sync** re-reads each synced calendar every `CALENDAR_SYNC_MINUTES` (15) inside the server (`CALENDAR_SYNC=off` turns it off), keeping events from 400 days back (past shoots pace the next one) to 400 ahead, and tells managers once about each new shoot it finds. Clients with `scripts_required` off are never in Shoots to plan or the planning reminders.
- **Paste notes** calls the Anthropic API, only when `ANTHROPIC_API_KEY` is set. Each person can run one read at a time and 30 an hour. If the API fails, the person gets a clear message and nothing is created.
- **The second look** (`server/second-look.ts`) calls the Anthropic API too, only when `ANTHROPIC_API_KEY` is set (`ctx.thumbCritic`; `Bootstrap.secondLook` tells the client, which shows the button only then; without it the route is 503 `not_configured`). It mirrors Paste notes: the SDK loaded on first use, structured output (no lengths in the schema itself, since the SDK checks its answer against it after the call; `tidySecondLook` trims and cuts instead), the same error mapping, and one look at a time per person and 30 an hour (a kept look is returned without a call and doesn't count). It sends the option (over 7 MB is 413 `too_big`, before anything is sent), then up to three of the client's current winners from its other briefs that this designer may open (`DESIGNER_FILES`), newest first, while the images stay inside about 24 MB of base64, then the brief, the client's brand voice and guidance, and its brand kit's colours (names and hex), do's and don'ts as text. A refusal, an answer cut short or one that can't be used keeps nothing, and the designer can ask again. It's advice: sending a round never waits on it.
- **AI brief ideas** (`server/brief-ideas.ts`) call the Anthropic API too, only when `ANTHROPIC_API_KEY` is set (`ctx.briefHelper`; `Bootstrap.briefIdeas` tells the client; without it the route is 503 `not_configured`). It mirrors Paste notes: the SDK loaded on first use, a text-only request with structured output (no lengths in the schema; `tidyThumbIdeas` trims, cuts at a word break, drops words on the image that don't fit or repeat the title, and drops repeated ideas), the same error mapping, and one ask at a time per manager and 30 an hour (counted only when a request is sent). It sends the video's title, the client's name, brand voice, guidance and the brand kit's do's and don'ts, the shoot's title and date when one is chosen, and the client's last 10 picked briefs, newest pick first (their titles, what they asked to show and their words on the image). A refusal, an answer cut short or one with fewer than `THUMB_IDEA_COUNT` usable ideas is 422. Nothing is saved: an idea only fills the form.
- **Content roadmaps** (`server/roadmaps.ts`) call the Anthropic API too, only when `ANTHROPIC_API_KEY` is set (`ctx.roadmapReader`; `Bootstrap.roadmapImport` tells the client; without it the import is 503 `not_configured`). It mirrors Paste notes: the SDK loaded on first use, the PDF sent as a document block with structured output (`ROADMAP_SCHEMA`, with no nullable field: an absent value is "", since union types nested in lists make the schema too complex for the API to compile), the same error mapping, and one read at a time per manager and 20 an hour. A refusal, an answer cut short or one with no video with a real publish day (`tidyRoadmap` returns null) is 422, and nothing is saved.
- **YouTube** (`server/youtube.ts`, `ctx.youtube`, created in `server/index.ts` with or without `YOUTUBE_API_KEY`; tests pass a stand-in): it never fetches a pasted link, only addresses built from a video id on `www.youtube.com`, `i.ytimg.com` and `www.googleapis.com`, over https. Every read has one 10-second timeout (`YOUTUBE_TIMEOUT_MS`) covering its redirects and body, follows a redirect only on the same host (at most 3; `redirect: 'manual'`), and refuses a body over its cap rather than cutting it short (256 KB for JSON, 4 MB for a watch page, `YOUTUBE_IMPORT_LIMITS.pictureBytes` for a thumbnail and `previewBytes` for a lookup's preview). Title and channel come from oEmbed (404 or 400 is not found, 401 or 403 private, anything else unreachable), the channel's page from its `author_url` either way, so matching a channel to an earlier import's client doesn't depend on the key. With the key, the Data API v3 gives the title, channel and publish date, and when it can't be asked (a bad key, the quota) the reader goes the keyless way: the publish date from the video's own page (`datePublished`, else `"publishDate"`, else `"uploadDate"`), or none, and the manager types it. Thumbnails are tried biggest first (`maxresdefault`, `sddefault`, `hqdefault`; a 404 is YouTube's placeholder), and every picture, the preview included, is sniffed by its own bytes (`imageInfoOf`); YouTube's Content-Type is never trusted, stored or served. Every failure is a plain message for that row (`YOUTUBE_PROBLEMS`), and the API key is only ever in the googleapis address: never in an answer, a log or an error.
- **Shoot estimates** (`server/shoot-estimator.ts`) call the Anthropic API too, only when `ANTHROPIC_API_KEY` is set (`ctx.shootEstimator`). The panel asks `POST /api/shoot-forecast/estimate` by itself once no documents are left to count; one request covers up to 12 clients whose history changed, with every candidate's history so Claude sees the team's rhythm. A history is its shoots (site and calendars), scripts and documents, other calendar events naming the client, the client's notes and the rule's estimate; Timeliner's video counts go with it but aren't part of the fingerprint, so a new video doesn't ask again. An answer whose date isn't after the last shoot is kept without a date (the rule shows). A failure keeps nothing.
- **Script counts** (`server/doc-counts.ts`) call the Anthropic API too, only when `ANTHROPIC_API_KEY` is set (`ctx.scriptCounter`). The Overview's Next shoots to book asks `POST /api/shoot-forecast/read-documents` by itself while documents of the shoots it counts from are unread; each call reads up to 6, one run at a time per server. A batch's document is its scripts PDF from Timeliner, else every document its writers sent (each script's newest; only when every script was sent in one). Only Google Docs (exported as text) and Drive files are fetched, from addresses built from their id; uploaded files come from `files`. A count, or why there's none (a private doc, a Word file), is kept in `document_counts` by the document's key (`pdf:<task>:<file>` or `sent:<submission>`), so each version is read once; a network, Timeliner or AI-service failure keeps nothing, so it's read next time.
- **Timeliner** (`server/timeliner.ts`), only when `TIMELINER_API_KEY` is set:
  - On start-up (once) or from Settings → Timeliner, the server registers a webhook (`TIMELINER_EVENTS`: `version.uploaded` and `file.uploaded`, plus the `task.*` and `project.trashed` messages for the Editors tab) pointing at `PUBLIC_URL` (or `RENDER_EXTERNAL_URL`) + `/hooks/timeliner`, and keeps the signing secret Timeliner returns in `settings`. Already connected, start-up adds any events it lacks (best effort: a read-only key can't) and leaves it switched on or off as Timeliner has it; Connect in Settings switches it back on.
  - `POST /hooks/timeliner` is public and outside `/api` (so the same-page header check doesn't apply); it refuses a message unless `X-Timeliner-Signature` checks out against that secret and is under five minutes old. Each message id is claimed in `timeliner_events` before anything happens, so a repeat is a no-op.
  - **A batch is found by its PDF's task.** An upload on a task already in `timeliner_pdfs` is a new version of that PDF: it goes to the same batch, whatever its name or date. A new PDF's client is the one whose PDFs sit in that project, else the one the Timeliner brand or project is named after (a batch's old `timeliner_project_id` is only this hint). Its batch is then a date or word of one batch in its name, else the shoot waiting for its scripts from 45 days after to 3 days before the day the PDF's task was made (never one whose scripts were all delivered by hand, without a PDF), else a shoot just behind that is still waiting, else the client's only undated batch waiting (`placePdf`). Two waiting shoots within 3 days, a name pointing at a batch that already has its PDF, a name like the PDF of a shoot still ahead, or only a shoot delivered by hand around then: it waits for a manager, with the likely batch suggested. Pick batch links it (`how = 'manager'`), offering every batch still without a PDF around then, approved scripts or not. It also moves a PDF linked to the wrong shoot, once none of the scripts it delivered there are still delivered (the manager undoes that delivery on the batch's page first; Move, which would undo it too, isn't built).
  - Each version delivers the batch's approved scripts through `applyScriptAction` with `viaTimeliner`, which records the delivery with `source = 'timeliner'`; one with nothing new to deliver is `new_version`. The link row is locked first, then the batch row. Editors with an open video from that batch are told once per version.
  - Uploads on a video's task (one that held a video file) are ignored; a file put straight into a project counts only when its name says "script" or names a batch, and is a new version of a linked file with the same name only while that file's shoot isn't past.
  - Lookups (task, project, brand, members) are best effort: when Timeliner can't be reached the upload is matched on what's known, or kept as unmatched for a manager to place.
- **Timeliner sync** (`server/editing.ts`, `syncTimeliner`), only when `TIMELINER_API_KEY` is set:
  - **Polling is the baseline.** Every `TIMELINER_SYNC_MINUTES` (5; the first 15 seconds after start-up) inside the server (`TIMELINER_SYNC=off` turns it off), and on Read Timeliner now (`POST /api/editing/sync`). It only reads, so a read-only key works. The timed read uses `ctx.realDb ?? ctx.db`, never a practice copy.
  - A read takes members, brands, tasks newest first (at most 30 pages of 100; trashed, archived, document and long-finished tasks are dropped), who is on each brand those videos are under (one call per brand, open videos' brands first, at most 60; a brand whose list fails, or that Timeliner says it doesn't have, keeps its last one and is counted as skipped; a list with an entry that can't be read never takes anyone off the brand, since that entry may be its editor: whoever it could read is added, and the rest stay as read last), the projects open videos sit in (names and sub-folders, re-read at most hourly) and the last step move of videos whose step changed (capped per read). A 429 or no connection stops these optional lookups for that read.
  - **Real data is read leniently.** Every task, member, brand, brand member, project and sub-folder is checked field by field with zod (`taskSchema`, `memberSchema`, `brandSchema`, `membershipSchema`, `projectSchema`): an odd field (null, missing, another type, a number for an id, an epoch for a time, an odd item in `assigneeIds`) takes a safe default; only an item with no usable id (or a brand or project with no name) is skipped, counted in the read's `skipped`, and its id logged once. One odd item never fails the read. A list answer that isn't a list (a 404, an HTML page) is an error, never an empty list, so it can't empty the copy; a member list none of which can be read keeps the last members. A webhook task that can't be read leaves its last copy as it is.
  - **Its lock:** everything is written in one `db.tx` under `LOCKS.timeliner`, which the webhook's one-video write also takes. A row written after a read began isn't overwritten by that read, and a removed id stays in `timeliner_removed` so an older read can't write it back. A complete read removes tasks it no longer lists; one stopped by the page cap removes only within the stretch it read.
  - **The webhook makes it faster:** when connected, `task.*` and `project.trashed` messages go to `applyTaskMessage`, which re-reads that one task (or removes it). The message is answered even when the task can't be read; the next timed read catches up.
  - **Matching** (`rematch`, under the same lock after every write, and after a pin): the whole copy is matched again by `matchVideos` in `server/matching.ts`. A video whose brand (or project) is no site client is `no_client`, and one whose client has no scripts on the site is `no_scripts`: normal work with no batch, never counted as not matched (`isNotMatched` in `shared/workflow.ts`). Videos go by date: the shoot that had just happened when the video was made in Timeliner (raw camera clips never take the shoot after, and never a script number); a titled video takes the shoot whose raw clips its editor has been cutting; the folder's word (Organic, Ads) only decides between batches of the same shoot. A pin wins; a video that has been in review keeps its batch (unless it moves folder, or it was matched by date alone before anyone had it and is then given to its first editor). Raw clips by their date and titled videos by their editor's raw clips are sure; a titled video by its date alone shows "matched by date". Linked scripts PDFs and tasks whose file is a document aren't videos: a read keeps their step, newest file and trashed state.
  - **Whom a video belongs to** (`OWNER_IDS` in `server/editing.ts`, the one place it lives): its assignees in Timeliner and nobody else, so the site matches Timeliner's assignee filter exactly. A video nobody is assigned to is nobody's ("not assigned"), however many editors its brand has. The board, an editor's Home, I'm on this, the scripts PDF link, the new-version notice, the shoot an editor's raw clips are from and their last finished video all go by it. Who is on a brand only names the client's editor (`IS_BRAND_EDITOR`, read into `brandEditors`): its editor in Editors by client, whom to give its unassigned videos ("usually X"), and the two-editors flag; a brand member with nothing assigned is in `peopleOf` for that naming but gets no card unless they're on the site (one who isn't on the site is in the board's `toAdd`, below). A brand's editor is a brand member with the brand role `editor`, not `automatic` (a workspace admin's access to every brand), still active, and not a workspace admin, supervisor or guest. Only video editors are editors: a member whose email is a site writer's, manager's, Admin's or thumbnail designer's (`SITE_NON_EDITOR`: the roles `isEditor` says aren't editors, and the kinds in `NON_VIDEO_EDITOR_KINDS`) is never one of a brand's editors nor a video's owner, so a video only they are on is not assigned. Thumbnail designers never get a card, aren't matched by name, and don't hear when a shoot's scripts are final or it moves (`editorIds` in `server/core.ts`).
  - **Steps** (`videoState` and `TIMELINER_STEP_LABEL` in `shared/workflow.ts`): the team's steps are To be edited (`toDo`) → Needs review (`inProgress`) → Revisions requested (`inRevision`) → Internal approval (`supervisorApproval`) → Awaiting client review (`clientApproval`) → Approved. So `inProgress` is in review: off the editor's plate, in Waiting on you, and it ends a focus and clears a done mark. The exact step name and when it moved there come from the video's history (`STEP_GROUPS`) for every step past To be edited.
  - **The board** (`loadBoard`): a card for every Timeliner member with videos assigned in the copy (any state) and every video editor on the site (`peopleOf`; a brand's editor with nothing assigned is named, without a card unless they're on the site). A member is matched to a site account by email (their taps count), else by name (any case, spacing or accents) to someone on the site with no Timeliner work under their email (flag `email_differs`), else they're only in Timeliner (flag `not_on_site`, or `no_site_access` with the city, time zone and hours of the same name in Settings → Editors), unless their Timeliner email is a deactivated (not removed) account on the site (`Loaded.deactivated`): then the flag is `deactivated`, to reactivate them in Settings → Team, since adding that email again would clash. A Timeliner admin, supervisor or guest (`REVIEW_ROLES`) on a video is reviewing it: they never count as its editor (`editorsOn`), have a card only for videos nobody else is on (`onCardOf`, so such a video isn't on nobody's card), and are never flagged to be added as an editor. A site video editor with nothing in Timeliner gets `nothing_assigned`. Someone deactivated in Timeliner with nothing open gets no card. A brand's editor (`IS_BRAND_EDITOR`, so never a reviewer, automatic access, someone deactivated there, or anyone the site knows as something other than a video editor: `SITE_NON_EDITOR`) with no video assigned, on a brand with videos in the copy, gets no card either: when they aren't on the site (no account with their Timeliner email, not even a deactivated one; nobody by their name: the same matching as above) they're in `toAdd` (`peopleToAdd`) with their Timeliner email, the clients they're the editor of, their flag (`not_on_site`, or `no_site_access` with that Settings → Editors entry's city, time zone, hours and `editorId`), once per name and never someone with a card. A `no_site_access` card carries `editorId` too. Neither reaches `GET /api/editing/me`. Totals count everyone's work, each video once. Each client (the site's client, else the Timeliner brand) has an editor: the editor on its brand in Timeliner (`editorFrom: 'client'`; with several, the one with the most of its videos); else whoever has the most of its videos made in the last 60 days (a tie: the most recent), counting only a video's editors, and never someone who has left Timeliner. A client with more than one editor on its brand is flagged ("has 2 editors in Timeliner"), else one whose open videos are with more than one editor is flagged as split; its unassigned videos (grouped by client, or by Timeliner brand, never across them) suggest its editor. Only videos made on or after `settings.one_editor_since` (Settings → Timeliner; Oct 9, 2026, when the rule began), in HQ time (`onOrAfterDay` in `shared/dates.ts`), judge the rule (`underRule`): the split, the two-editors flag and the editor worked out from videos; older ones still count everywhere else. A client with none (`beforeRule`) is never flagged and names only the one editor on its brand. Clients on the rule are listed first, flagged ones first among them. Nothing here is stored: it's worked out from the copy on every load.
  - After every write, a focus whose video left the editor's plate, was given to someone else or is gone ends by itself. One still running after `FOCUS_STALE_HOURS`, or outside the editor's working hours, stays as it is but isn't counted as editing now (`isFocusStale` in `shared/workflow.ts`). A failed read keeps the copy and stores Timeliner's message in `settings.timeliner_sync_error`; a good one sets `timeliner_synced_at`.
- **No email:** the app never sends email. Sign-in details are copied by hand.

## Invariants (break one and something real breaks)

1. Every number on every screen (progress, stages, charts, counts) is computed from script rows (a thumbnail brief's state and counts, and a designer's growth figures, from its rounds, decisions and pins). Nothing stores a total. The one exception is the next-shoot estimate, which goes by how many scripts Claude counted in a past shoot's document (`document_counts`) when it has; it never changes progress or a script.
2. A script has at most one assignee.
3. Only `applyScriptAction` changes a script's status.
4. The written-so-far counter never changes a script's status.
5. A shipped migration is never edited.
6. View as never writes to the real workspace. A Recording-mode write never reaches it either.
7. Every `/api/` route has a guard (or is deliberately public), and is listed in `test/access.test.ts`.
8. Secrets are never sent to the browser. The client bundle reads no environment variables.
9. Every user-visible change has a What's new entry in `shared/changelog.ts`.
10. An editor's kind (`users.editor_kind`) exists only while their role is `editor`; the database refuses anything else (`users_editor_kind_check`). So every write that changes someone's role sets their kind in the same statement, and a thumbnail designer's kind or role can't change while they have open briefs.
11. Writers and video editors never open a thumbnail option, and nobody but its designer (or an Admin viewing as them) sees an unsent tray. A designer sees another designer's options only once picked (the current winner), and the pins on a round only when they sent it. A second look is only ever shown to the option's maker (not even to an Admin viewing as them). A reference board, and every picture uploaded to it, is only ever its designer's (or an Admin viewing as them). A portfolio is only its designer's and the managers', and never ranks or compares designers.
12. The server never decodes an image: an upload's type and size come from its own header bytes (`server/images.ts`), a thumbnail read from YouTube's too (never its Content-Type), and "Pick colours from logo" reads the logo in the browser.
13. The server never fetches a YouTube link someone pasted: it reads the video's id (`youtubeVideoId`) and builds its own addresses on YouTube's fixed hosts. A YouTube video is on at most one thumbnail brief that isn't cancelled (`thumbnail_briefs_youtube_key`).

## Testing

- **Commands:** `npm run verify` runs typecheck, lint (zero warnings), tests and build, which is what CI runs. `TEST_DATABASE_URL=postgres://… npm test` runs the suites on a real PostgreSQL; it wipes that database's schema first. CI also runs the API suites on Postgres 16.
- **`test/api.test.ts`** is one long scenario that runs in order. Don't filter it with `-t`, because later tests depend on earlier ones. Add self-contained cases to `test/workspace.test.ts` with `freshDb()`, or write a new file.
- **`test/access.test.ts`** checks every route against its `ACCESS` table, and that anonymous users, writers and managers are refused where they should be.
- **Pure rules** (dates, workflow, parser, config) have unit tests in `test/*.test.ts`. Change a rule and add a case for it.

## Deploy and operations

- **Build:** `npm ci && npm run build`. **Start:** `node --max-old-space-size=200 --max-semi-space-size=2 dist/server/index.mjs`. Use `node` rather than `npm start`, which keeps npm running alongside and uses memory. Health check: `/healthz`.
- **Production needs `DATABASE_URL`.** The server refuses to start on the host's temporary disk. The first Admin comes from the `MANAGER_*` variables, used once, on an empty database.
- **Backups** are the database host's. Pick a plan that has them. Uploaded files are in the database, so a database backup covers them.
- **Rollback:** deploy the previous commit. Migrations so far only add or widen, so older code runs on a newer schema. A migration that isn't additive must say so in its comment, with how to undo it.

2. Reuse what's in `shared/`, `server/http.ts`, `server/records.ts` and `client/src/components/ui.tsx`.
3. Keep the change to what was asked.
4. Add or update tests.
5. Run `npm run verify`.
6. Add a What's new entry.
